Every stone has a source.

Cairn is an agent for Odoo development. It learns only from the source code you give it, and shows the file and line behind every answer.

Read the roadmap See how it works

Confident answers, wrong version.

APIs move between versions
A renamed method or a moved field reads fine until it fails in a running system.
One version still drifts
A checkout from early in the year and one from the end of it are not the same code.
Guesses look like facts
An assistant that cannot show its source cannot be audited, so every claim needs a place to check it.
Principles

An answer you can check.

Every answer carries one of three labels, so you always know how much weight it can bear.

/ask <your question>
verified @<snapshot> <addon>/models/<file>.py:<line>
inferred basis: what the reasoning rests on
unverified needs: the file or module still to read
Illustrative format. Placeholders in angle brackets.
Cited
Every stored fact carries a file, a line, the Odoo version, a snapshot id and a file hash. No source, no fact.
Versioned
Knowledge is kept per Odoo version and per source snapshot. Snapshots are immutable, and a refresh adds a new one.
Isolated
Each project keeps its own memory, skills, specs, tests and containers. Nothing moves into the core unless you promote it.
Consented
New skills, imports and rollbacks are proposals first. Cairn grows only when you say yes.
How it works

Index first. Source on a miss.

Ask
You ask a question about a version of Odoo.
Look up
Cairn queries the index for the pinned snapshot. A hit is answered with its file and line.
Read
On a miss it reads the relevant source files and records every file it touched.
Remember
It answers, then adds what it learned to the index, with provenance.
A read tracker, not a black box
Each source file is marked unread, indexed, read or skipped, with how deeply it was understood. Coverage per addon shows what Cairn knows and what remains.
Snapshots that do not overwrite
When the source of the same version changes, Cairn creates a new snapshot and re-reads only the files that changed. Projects stay pinned to the snapshot they were built on.
Two layers
The core holds knowledge per version. A project reads it and never writes to it. Anything reusable moves up only through an approved promotion.
Planned capabilities

From source to shipped module.

Knowledge
Scripted structural indexing of Odoo source, immutable snapshots with shared objects, coverage tracking, and refresh for new source of the same version.
Building
Module scaffolding, customization, front-end work (views, OWL, QWeb) and porting addons from one Odoo version to another.
Running
Dev-container control, module install and upgrade, and a debug loop that traces errors back to the source. Development environments only.
Quality
Odoo conventions and clean code, Big-O and query-count analysis for non-trivial solutions, and a quality gate aligned with ISO/IEC 25010. Aligned with, not certified.
Process
A functional knowledge layer, discovery and fit-gap, and spec-driven development with a method you plug in.
Governance
A consent gate for skills, quarantined imports, export with a checklist, and a versioned agent you can roll back.

Boundaries

What Cairn will not do.

It does not ship Odoo source, or any knowledge index derived from it. You provide the source and Cairn builds its knowledge locally.
It does not touch production. Container and database actions apply only to development containers declared in a project.
Its safeguards are guardrails, not a sandbox. Run it on a development machine with no production credentials.
Its answers are only as good as the source and index it has. Low coverage means more answers marked unverified.
